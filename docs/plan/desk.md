## What we learned first (2026-11-25)

- **T3 has a CLI that does the hard part.** `~/.t3/bin/t3 thread send <thread> -` sends a message (a busy thread gets it as its next turn), `t3 thread start <project> - --provider … --model … --option effort=…` starts a thread, and `t3 thread show <thread> --messages N --json` returns the thread state (status, model, `pendingRequestCount`, …) and the latest messages' text. The CLI handles T3's own authentication, so Axiom needs no pairing. Limits: `send` cannot change the model or effort of an existing thread; there is no CLI command for approvals.
- **Claude Code's `Stop` hook payload carries `last_assistant_message`**, so the hook gets the reply text directly (also `transcript_path`, `cwd`, `effort`).
- **`claude -p --model haiku --no-session-persistence`** runs a one-off summary on the owner's subscription without leaving a session behind.
- **Replying to a direct Claude Code session** is `claude -p --resume <id> --model … --effort …` in the session's folder. That is only safe when the session isn't open in a terminal (Axiom knows: it has seen `SessionEnd`). While it is open, the card offers the copy-resume command instead.

## D5 as built (2026-11-25)

- **T3 questions:** the Desk card shows a thread's pending `user_input` question (header, text, options; multi-select; free text) and answers it through T3's MCP endpoint (`POST http://127.0.0.1:<port>/mcp`: `initialize`, `notifications/initialized`, `tools/call t3_pending_request {action: "respond", threadId, requestId, answers}`). The bearer token is minted per answer with `t3 auth session issue --scope orchestration:read --scope orchestration:operate --ttl 5m --label axiom --subject mcp-client --json` (T3's MCP endpoint only accepts sessions whose subject is `mcp-client`; a default session gets 401 `invalid_mcp_credential`), used once, revoked with `t3 auth session revoke`, and never stored or logged. `answers` maps a question id to a label (or free text), or to a list of them for a multi-select question.
- **T3 permission approvals:** the MCP tool cannot approve one (T3's own description says so). T3's internal `runtime-request.respond` command does take a `decision`, but only over its WebSocket RPC, which is not a supported surface. The card shows the request with an **Open in T3** link.
- **Claude Code approvals:** `axiom hook permission` (`PermissionRequest`; installed with a 620 s hook timeout) records a row in `approval` (migration 0006), marks the thread waiting on the owner, and polls the database every 500 ms for the owner's decision (`approvalTimeoutSec`, default 600, 10 to 600). It prints `{"hookSpecificOutput":{"hookEventName":"PermissionRequest","decision":{"behavior":"allow"}}}` or `{"behavior":"deny","message":"..."}`; on a timeout, SIGTERM or any error it prints nothing, so Claude Code asks in the terminal. No-op for unattached sessions, `AXIOM_INTERNAL=1` and T3-run sessions. A pending approval whose hook process is gone (the owner answered in the terminal) is expired by the server.

## D13 as built (2026-11-26)

- **What Claude Code does (verified with `claude -p` 2.1.325 on throwaway folders):** the `PermissionRequest` input carries `permission_suggestions` (the terminal prompt's choices: `addRules` such as `Bash(npm run *)` to `localSettings`, `setMode` `acceptEdits` for the session, `addDirectories`) and `permission_mode`. An allow with `updatedPermissions` applies them: an `addRules` for `session` covers later calls at once; for `localSettings` it writes `.claude/settings.local.json` but does not reach the running session (the next matching call still asked); `setMode acceptEdits` works; `setMode bypassPermissions` is ignored.
- **Storage:** migration 0017 adds `approval.suggestions` (the cleaned suggestions, JSON) and `approval.applied` (what the allow sent back, JSON; NULL for a plain allow). Core `permissions.ts`: `cleanSuggestions` keeps only allow rules, `acceptEdits` and directories (at most 6, no duplicates, strings up to 500 characters; bypass, `plan`, deny/ask rules and unknown kinds are dropped); `describePermissionUpdate` labels them ("Always allow Bash(npm run *) in this project", "Accept all edits for this session", "Allow access to … for this session"); `updatesToApply` adds a session copy to a rule saved in a settings file.
- **Decision:** `decideApproval(id, "allow", message, owner, { suggestion: i })`, and `POST /api/approvals/:id` `{ decision: "allow", suggestion: i }` (400 for a deny with a suggestion or an unknown index). History: an `authorization` with `standing: true` and the rule as its scope ("Allowed Bash: $ npm test, and: Always allow Bash(npm test:*) in this project"). The hook prints `{"behavior":"allow","updatedPermissions":[…]}`.
- **Card:** `requests[].choices` (`{index, label}`); under Allow / Deny a group "Allow, and don't ask again:" with one button per choice (hidden while denying). The live status says "Allowed (<choice>)".
- **Checked end to end:** a real `claude -p` session attached in a temp database ran three `npm run` calls; Axiom got one approval with the suggestion `Bash(npm run *)`, the owner side picked it, the other two ran without asking, and the project's `.claude/settings.local.json` gained the rule.
- **Not covered:** T3-run Claude threads (T3 asks for those itself, and its API cannot approve them); bypass mode; seeing or removing standing rules in Axiom (02, Q17).

## D14 as built (2026-11-26)

- **What Claude Code does (verified with `claude -p` 2.1.325, a logging `PermissionRequest` hook, throwaway folders):** `--permission-mode manual` asked for every call; `acceptEdits` ran Write, `touch` and `mkdir` but asked for `node` and `npm`; `auto` ran `node` and `npm` without asking; `bypassPermissions` works from the flag alone and never asked. A `--resume` run without the flag asked again: the mode is not kept with the session.
- **Modes offered** (core `PERMISSION_MODES`): `manual` (Ask, the default), `acceptEdits`, `auto`, `plan`, `bypassPermissions`. `dontAsk` is left out (it denies whatever is not pre-allowed, so an unwatched run just fails).
- **Server:** `POST /api/threads/:id/send` and `POST /api/topics/:slug/threads/new` take `permissionMode`; a Claude Code run gets `--permission-mode <mode>`. The choice is stored as the internal setting `threadPermissionMode:<thread id>` and reused when a later send gives none. The terminal resume command (the 409 for an open session) includes it. The Desk API has `threads[].permissionMode` (Claude Code threads; null when never chosen). A mode for a T3 thread, existing or new, is a 400: T3 keeps its own mode per thread, its CLI has no option for it, and T3's MCP launch cannot go above the caller's own mode.
- **Web:** `lib/permissionModes.ts` (labels and one-line hints; Bypass is set apart in the menu with "Never asks: anything runs, destructive commands too"). The chip `Permissions` in `ReplyBox` starts from the selected thread's last mode and follows the thread picker; in `NewTopicDialog` it applies to a Claude Code first thread. Off for T3, with the reason.
- **Not covered:** sessions the owner starts in a terminal (their mode is whatever the terminal set; Axiom does not read it yet, though hook payloads carry `permission_mode`); T3 modes.
